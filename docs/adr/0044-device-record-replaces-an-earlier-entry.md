# ADR-0044: A device record may say it replaces an earlier entry of the same device

- Status: Accepted
- Date: 2026-11-25
- Decision: D44 in `docs/decisions.md`
- Amends: `crypto.md` 7.4 (device records), `pairing-recovery.md` 4 step 8 (removing the vault from a device)
- Task: FIG-232

## Context

"Remove this vault from this iPhone" forgets the device keys (`pairing-recovery.md` 4.8). Adding the vault again
from Google Drive or iCloud Drive then creates new keys and so a new device id and a new record. The old record
stays in `devices/` (sync never deletes), so the Devices list shows the same phone twice, or more after more
round trips, one of them with only a random id. Found by the maintainer on a real iPhone (FIG-232).

Keeping the keys across a removal was rejected (below). Deriving the keys again from the master password and
Secret Key was rejected too: anyone who learns those two could then recompute the device's signing key, which
`crypto.md` 4 says never leaves the device. Revoking the old entry rotates `VK` and forces every other device to
a full unlock, which is far too much for the same phone coming back.

## Decision

1. A device record (`crypto.md` 7.4) may carry one more member, `replaces`: the 16 byte device id, 32 hex
   characters, of an earlier entry of the same device. It is part of the signed record like every other member.
2. It is a hint for the device list and nothing else. It changes no key, grants nothing, revokes nothing, and
   the earlier entry's ops stay valid (`sync.md` 9). A list does not show a live entry that another live device `replaces`: it
   is the same device (FIG-234). A `replaces` equal to the record's own id, or one that
   does not read as an id, is ignored. An id with no record hides nothing.
3. An app that removes the vault from a device keeps the device's own id, only the id and no key material, in
   its keystore (iOS: the keychain, which survives deleting the app). When the vault is added again and the
   unlock writes a new record, it sets `replaces` to that id. A first install, or a phone whose id is gone (a
   new phone, a wiped keychain), writes no `replaces`, which is right: it is a new device.
4. Rotations re-sign the remaining records and keep `replaces`. A client that does not know the member and
   re-signs a record drops it, which only brings the earlier entry back in the list; it is never a failure. A
   record with `replaces` verifies in any client, since the signature is over the JCS of the whole record, so
   `min_format_version` does not change.
5. A device that is revoked is not a device again (`pairing-recovery.md` 4.6): it writes no record, so it
   writes no `replaces`.

## Consequences

- `crypto.md` 7.4 and `pairing-recovery.md` 4.8 change. `signatures.json` gains four cases (sign and verify a
  record with `replaces`, a changed one, one added to a record signed without it), generated by `generate.py`
  and checked by `vectors.rs`.
- Rust: `DeviceKeys.replaces` (not stored with the keys), `DeviceInfo.replaced_by`, tests in
  `figlock-core/tests/replaces.rs`. FFI: `DeviceKeysHandle.set_replaces` and `DeviceEntry.replaced_by`.
- Any holder of `VK` can already write a device record, so one could also write a `replaces` naming another
  device, which hides that entry from the list. It cannot revoke it or touch any data, and the entry is still
  there to revoke by id in the CLI.
- Entries that already exist from earlier re-adds are not linked; they can be revoked by hand.
- The desktop and the CLI do the same when they remove a vault (follow-up); until then their re-adds still
  make a new entry.
- Not covered: joining again with a new invite (`pairing-recovery.md` 3), which writes the record from the
  trusted device. A follow-up can carry the hint in the join request.

## Alternatives considered

- **Keep the device keys on removal.** Same device id, no new field. Rejected by the maintainer: a "removed"
  vault would leave signing and agreement keys on the phone.
- **Derive the device keys from the vault secrets.** Same id every time with nothing stored. Rejected: the
  signing key would no longer be held only by the device.
- **Revoke the old entry on removal.** Rotates `VK` and forces a full unlock everywhere; a device cannot revoke
  itself either.
- **Match entries by name.** Two phones may share a name, and a renamed phone would not match.
- **Delete the old record on removal.** Sync is a set union with no deletes, so it would come back.
